# 用户流程

## 1. 核心使用方式

Stella Fitness 必须顺着真实训练行为，而不是要求用户为 AI 改变训练习惯。

### 训练日

v1 默认直接复用用户提供的三阶段 XLSX 训练情况记录模板：

```text
打印对应阶段/训练页
  ↓
训练 + 在固定表格中用纸笔记录实际结果
  ↓
训练结束
  ↓
拍当前训练块或完整页面
  ↓
系统按固定模板结构化并标记不确定字段
  ↓
仅必要时请求最小补充
```

训练过程中不要求逐组手机输入，也不设计“每做一组和 Agent 对话”的默认流程。

首版不要求开发新的 ProgramSpec-driven printable generator。现成模板已经足够作为标准 UX 与 Tier A extraction layout。

详见：

- `training-log-template.md`；
- `printable-log.md`。

### 体重

用户以低成本形式定期输入：

```text
今天 68.4 kg
```

系统保留原始测量时间和修正记录，用趋势而不是单次数字做判断。

### 饮食

饮食记录是可选证据，而不是强制打卡。

优先级：

1. 用户确认的食物重量 / 包装营养标签；
2. 固定食谱或已校准常吃餐；
3. 文字描述 + 份量信息；
4. 单张食物照片估算。

照片输入必须输出识别项、估算区间、置信度与不确定来源，不得伪装为精确计量。

## 2. 训练日志结构化流程

现成模板主要包含：

```text
动作
重量
第一组 ~ 第六组
动作质量
问题备注
```

系统需要注意：

- `重量` 不总是 kg：引体向上可能记录弹力带颜色，俯卧撑可能记录姿势/负重；
- `第 x 组` 不总是 repetitions：平板支撑属于 duration；
- `动作质量` 是高/中/低主观信号，不等价于 RPE/RIR；
- `问题备注` 可能同时包含普通观点与安全相关描述，需要分流；
- 第 4 周周五存在特殊 `力量测试` layout，而不是普通训练 block。

### 图片看不清

只请求无法可靠恢复的最小字段，例如：

> “硬拉重量这一格无法可靠识别，请补充一个数字。”

而不是让用户重新手工录入整份训练。

### 空白字段

空白必须保持 unknown / absent。

即使 ProgramSpec 已知“今天应该做 4×10”，也不能因为图片里没写结果就自动填成 4×10。

## 3. 体重与周期监督

```text
新数据进入
   ↓
更新事实与指标
   ↓
证据是否达到分析门槛？ ── 否 → 静默/继续收集
   ↓ 是
Blind Diagnosis
   ↓
Audit + Policy Gate
   ↓
NO_CHANGE / OBSERVE → 静默或简短周报
COLLECT_MORE_DATA   → 只问最高价值缺失信息
ADJUST_*            → 给出有证据的调整建议
ESCALATE            → 停止增肌优化，转安全提示
```

## 4. 典型场景

### 正常进展

体重与训练表现符合预期，没有连续异常。

结果：`NO_CHANGE`。系统不为了显示存在感而改变训练。

### 用户带着结论提问

用户：“我觉得就是吃少了，是不是应该加碳水？”

流程：

1. 原话中的观点不进入 Blind Diagnostician；
2. Blind Diagnosis 先基于 EvidencePacket 完成；
3. Belief Extractor 单独提取“摄入不足 → 加碳水”的用户观点；
4. Auditor 比较观点与已冻结诊断；
5. Policy Gate 决定是否允许调整。

### 数据不足

若观察窗口中体重或饮食证据明显不足，系统应明确 `COLLECT_MORE_DATA`，而不是猜测停滞原因。

## 5. 非目标流程

- 实时动作视频纠正；
- 训练中持续语音陪练；
- 自动生成随机每日训练；
- 强制精确卡路里记账；
- 诊断疾病/伤病；
- 用情绪鼓励代替证据判断。
